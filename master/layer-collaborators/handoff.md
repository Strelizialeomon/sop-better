## 真人协作者 handoff

### 协作主线

- **业务 → 开发**：业务方定目标、验收、范围和产品形态；req doc 写正文，issue 只做索引和状态。开发接手前先验 doc 链接。
- **开发 → 业务**：范围、形态或验收需要变化时，在 issue 评论写清要拍什么、影响和证据，并标 `待业务确认`。
- **开发 → 开发**：方案、字段、契约和跨模块影响写 issue 评论；PR 评论只处理本次 diff。
- **PR 收口**：中间交付用 `Refs`；最终验收和关闭条件满足才用 `Closes`。

### 业务起需求

1. 开工先看待业务确认的 issue，再聊新需求。
2. 对话收口要钉死验收、主流程、范围和产品形态；新增或大改界面还要确认 UI 风格来源。
3. 先把 req doc 推到远端，再开 issue 指稳定链接；req doc 写“要什么”，技术实现留给开发细化。
4. 交棒后由开发推进，业务方只在业务裁决、联调和高风险闸出现。

### 不撞车与收工

- 每个任务有明确 owner；并行任务可并行派，但不能让两人静默改同一范围。
- 缺别的角色该交付的需求、契约或验收时，反弹并标 ⏸️ 待澄清，不能自行伪造。
- owner 说“收工 / 结束”时，按工作流落远端凭据；push、deploy、删除和其它高风险动作仍需单独确认。
