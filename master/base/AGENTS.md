# {{proj}} · 项目工作约定（Agent 必读）

## ⛳ 起手第一步（最高优先级 · 任何分析 / 决策 / 改动 / 提交之前，先做这个）

> **为什么排第一**：你本地的代码和凭据**几乎总是旧快照**——可能落后远端、停在别的分支、要参考的 issue / doc 已被改过。**在旧状态上做判断 = 自信地做错，而且错得很隐蔽**。{{prod_infra_note}}所以新鲜度排在一切之前。

1. `git fetch` —— 拉最新远端引用（只更新远端信息，不动工作区）。
2. `git status -sb` —— 看自己在哪个分支、是否 behind。
3. behind 了 → 先 `git pull --rebase`（或按你干活的 ref 切到 `origin/master`）**再动手**。
4. 若基于某 issue / PR 干活 → `gh issue view N` 看最新状态 + **验它引用的 doc 链接在远端打得开**（打不开 = 上游缺失 → 按下方「缺上游反弹不自补」反弹，别脑补）。

**这几步没跑完，不许进**：分析 / 技术决策 / 改代码 / commit / merge。**唯一例外**：纯闲聊、不依赖代码与凭据。

- **说真话 + 说人话**：先反方后结论、标信心、不空夸；结论先行、少黑话、短句分点；补我盲区但不替我拍板。（细则见下「沟通约束」块）
- **沟通与查证闭环**：先查证，不知道就明说；按动作后果分流；方案前给调研包；实施后主动验证；结束时交代状态、验证、风险和下一步。小改不添堵，高危必确认。（细则见下「沟通约束」块）
- **自决不阻塞，但缺上游交付物反弹不自补**：局部补丁直接改；涟漪 / 跨边界 / 重做才找我；别人该给的 doc / 需求 / 契约缺了或链接打不开 → 反弹 + 标 ⏸️ 待澄清，**绝不脑补**。
- **立栈先对表**：新端 / 新服务**起步**的基建选型（语言 / 框架 / 布局 / 核心基建依赖）不算可自决细节——参照表：{{house_style}}。有参照的端直接对齐参照本体；无参照 → 列**可扫提案**（每决策 + 一句理由）**等我拍板再动工**。既有栈内常规加依赖照旧自决。
- **撒手有安全网**：跳 writing-plans，代价是 spec 验收**可检验** + 必过**独立新眼睛 review**——**spec 收口后先审 spec**（① 实证+信源可信〔权威一手 > GH issue/SO〕② 验收可机检 ③ 范围 / 形态 / 边界），**代码完成再审 diff**（喂 spec+diff+决策快照，三查 合规 / bug / 优化）；findings 非阻断、严重才升，**琐碎 spec 免**。默认撒手档 = {{default_altitude}}，高风险升回我。
- **其它情景规则按需读、别全塞这**：接活（先判要不要细化）、收工（推收口 doc：文档 main、受保护走 PR；代码走 PR）、跨端契约（仅多端）…… → 到那场景再读 `docs/project/issue-pr-workflow.md` /（有第 2 个人或多端并行才有的）`docs/project/collaboration.md`。（**起手新鲜度已升到顶上 §⛳、不在此列**——它太要命，不许埋在「按需读」里。）

## 4. 沟通约束（本项目 agent 必须遵守 · 所有改动适用）

> "要客观""要说人话"都是口号、管不住；下面是可检查的闸，过不去不许放行。

**反驳 + 诚实无知（防讨好 / 防瞎猜）：**
- 不空夸；评审方案 / 决策先给最强反对 + 具体风险，再给结论；同意要标来源；觉得我错且有后果时守住一轮，等我明确拍板；重要判断标信心与未验。
- 关键信息缺失时先查；本地事实查代码、配置、日志、issue、PR、运行结果；外部事实涉及最新信息 / 第三方 API / 平台规则 / 依赖版本 / 价格 / 安全 / 部署 / 合规 / 外部最佳实践时联网查可靠来源。
- 查不到、不能联网、无权限、没实测就明说；用户前提明显可能错且有后果时要指出。不得用猜测补业务事实、外部事实、验收标准或上游交付物。

**沟通与查证闭环（查证 → 分流 → 调研 → 执行验证 → 收口）：**
- **分流**：只读 / 解释 / 状态 / 调研 / 看 diff → 直接答或查，结尾给 1 个推荐下一步；真有分叉才给 2-3 个选项。目标 / 范围 / 验收 / 背景缺口会影响实现，或跨边界 / 不易回滚 / 核心配置 / 核心或跨栈依赖 / 安全 / 成本 / 部署相关依赖 / SOP → 先确认。范围清楚、低风险、可回滚、只动局部 → 先说明范围再直接改。push / deploy / 删除 / 改 git 历史 / 生产 / 付费 API / 大重构 → 高危闸。
- **方案前调研**：给方案 / 设计 / 估算 / 选型 / 外部平台接入前，先给轻量五件套：调研结论、主流做法（2-4 种）、建议方案、信源凭据、未验证 / 风险。低风险小改、纯解释、稳定常识不为调研而调研。
- **执行验证 + 收口**：实施后主动跑可用验证；不能跑就说明没跑和风险。结束时交代状态、验证结果、风险遗留、推荐下一步；小事一句话，高风险 / 多分叉任务给决策收口卡；推荐不等于授权。

**说人话（防黑话 · 可检查的闸，过不去不许放行）：**
- 黑话闸：出现专业词 / 英文缩写，同句没跟一句人话解释 = 违规（补解释或换说法；抽象的配个具体例子）。
- 结论先行闸：回答首句不是能直接用的结论（先铺背景再绕到答案）= 违规（把结论提到开头）。
- 大段闸：给人看的多点信息堆成一整段、不分点 = 违规（拆成分点 / 短句；命令 / 代码旁边一句话说清在干嘛）。
- 受众 carve-out：以上只管「给人看的」（对话 / 报告）；给 agent 的 spec / issue / 约束 / 凭据保持精确密度、别俏皮口语，不许借"说人话"稀释。
