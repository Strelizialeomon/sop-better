# Issue + PR 工作流（agent 执行）

## 三件套分工

- **doc = 正文 / 真相源**：需求、设计、契约和长期决策写进 doc 或 ADR。
- **issue = 索引 + 状态 + 消息总线**：写当前状态、验收、阻塞，并链接 doc 和 PR。
- **PR = 交付凭据 + 收口动作**：写改了什么、怎么验、风险和关闭条件。

上游先把 doc 推到远端，再开 issue 指稳定链接；开发接活先验链接；过程变化写 issue 评论；PR 留验证；关闭条件满足才关 issue。

## 起手与取活

1. 先看 `git status -sb`，保护本地未提交改动。
2. 任务依赖远端状态时运行 `git fetch`，比较当前 HEAD 与 `origin/{{default_branch}}`。
3. 用 `gh issue view <N> --comments` 读取最新状态并验证 doc 链接。
4. 缺业务该给的目标、形态、验收或契约时，评论反弹并标 ⏸️ 待澄清；不能以“永不阻塞”为由自行补需求。

## Issue 生命周期

1. **开**：一项需求或缺陷一个 issue；正文保持薄，只放目标、验收和稳定 doc 链接。
2. **标**：阶段为评估中 / 开发中 / 已完成；待澄清、`待业务确认` 可作阻塞标记；每次开工先把 `待业务确认` 项主动展示给 owner；状态可用 ✅🚧⏸️⬜。
3. **跟进**：决策、范围、字段、风险、路线或关闭条件改变时写 issue 评论。
4. **关**：验收或明确关闭条件满足才关；中间交付保持 open。

spec 收口或实施路线改变时，在 issue 评论产出核心决策快照：问题、选择、放弃项与理由、边界、验收；控制在 30 行内，供代码新眼睛消费。

会改变后续判断的评论必须写清当前状态、动作、证据、判定、边界、残项和下一步。只贴链接、tag 或轻进度才允许短评。

## PR 生命周期

1. 从确认过的 `origin/{{default_branch}}` 创建 `<type>/issue-N-<slug>` 分支。
2. commit 前用 `$commit-msg` 读取 diff 生成或校验提交信息。
3. 中间 PR 使用 `Refs #N`；只有最终验收和关闭条件满足的交付使用 `Closes #N`。
4. PR 正文写改动、验证、风险、issue 和 doc 链接。
5. 代码完成后接受独立新眼睛 review；review 输入必须包含 spec / 验收、diff 和决策快照；非阻断 finding 直接修，严重问题才升级。
6. 低风险可逆改动可按项目约定自动合；生产、删除、付费调用、保护分支和不可逆动作必须回 owner。
7. 治理 doc、SOP、`AGENTS.md`、workflow、collaboration、PR 模板、`docs/contracts/` 和跨端骨架不属于低风险自动合，必须回 owner 人审。
8. 合并后校正 issue 状态；只用了 `Refs` 的 PR 不得误关 issue。

## 凭据保真

- 状态必须等于实际进展；搁置要写原因，做完要收口。
- 决策闸若仍依赖后续 spike 或数据验证，裁决后保持 open，并写清真正关闭条件。
- issue 评论保存长期路线和状态；PR 评论只处理本次 diff。
- owner 说“收工 / 结束”时，按本工作流把会话产物落成远端可打开的凭据；高风险动作仍需单独确认。
