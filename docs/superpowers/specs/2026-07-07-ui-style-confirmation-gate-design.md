# UI 风格确认闸设计

日期: 2026-07-07

状态: 待 owner review

## 1. 背景

当前 SOP 已经把“产品形态”列为业务要确认的内容:网页 / 后台按钮 / App 页面 / 定时任务等属于“要什么”,不能让 agent 默认成开发顺手的形态。

真实新问题是:需求和产品形态聊清楚后,如果任务会产出前端页面 / App 页面 / 可视化界面,Codex 仍可能直接实现,没有再确认 UI 风格。结果是功能对了,但视觉气质、信息密度、参考样式可能不符合 owner 预期。

本次只解决“有 UI 的任务要确认风格来源”。纯脚本、后端接口、数据处理、配置、测试、重构等不产出用户可见界面的任务不应被拖进样式确认。

## 2. 调研依据

本地依据:

- `STANDARD.md` §1.2 已定义产品形态属于“要什么”,业务角色要确认“长什么样”。
- `STANDARD.md` §1.3 的 spec 收口标准目前是“验收 + 主流程 + 范围 + 形态”,还没有显式覆盖“UI 风格来源”。
- `STANDARD.md` §1 附的分流规则要求:目标 / 范围 / 验收 / 背景缺口会影响实现时先确认;低风险局部补丁不要添堵。
- `PLAYBOOK.md` exp-004 证明:形态没确认会让非技术需求方被开发默认形态带偏。
- `PLAYBOOK.md` exp-020 证明:协作规则要按动作后果分层,同时写清低风险局部补丁的反向边界。

外部依据:

- OpenAI Codex best practices:复杂或模糊任务先 plan / interview user;提示应包含目标、上下文、约束、完成标准;重复有效的工作方式应沉淀到 `AGENTS.md`,并保持实用、短、准。参考: https://developers.openai.com/codex/learn/best-practices
- OpenAI AGENTS.md guide:Codex 会在开工前读取全局和项目级 `AGENTS.md`,更靠近当前目录的指令优先。参考: https://developers.openai.com/codex/guides/agents-md
- Figma design brief:设计 brief 通常要明确目标、受众、品牌规范、设计要求、交付物,并在应用前达成一致。参考: https://www.figma.com/resource-library/how-to-create-a-design-brief/
- AHRQ checklist design:清单有用,但过长或设计差会伤害执行;要按任务和使用者设计。参考: https://psnet.ahrq.gov/perspective/what-makes-good-checklist

## 3. 目标

1. 当任务会新增或大改前端页面 / App 页面 / 可视化界面时,agent 在实现前确认 UI 风格来源。
2. owner 不需要从零写设计 brief;agent 应给可扫选项,让 owner 做有依据的决策。
3. 纯脚本、后端、数据处理、测试、配置、重构等无 UI 任务不触发。
4. 已有界面内的小修、小 bug、文案微调默认沿用现有样式,不单独问。
5. 规则落点要短,并接到现有“形态确认 / 分流 / 自决不阻塞”体系,不新建一套重流程。

## 4. 非目标

- 不建立完整设计系统。
- 不要求每个 UI 小改都出 mockup。
- 不要求脚本 / CLI / 后端任务确认样式。
- 不改变“局部补丁直接改”的基本原则。
- 不同时启用 taste 系和 impeccable 系设计技能;若后续实现涉及前端设计,仍按全局约束二选一。

## 5. 推荐方案

采用“窄触发 UI 风格确认闸”:

```text
当任务会新增或大改前端页面 / App 页面 / 可视化界面时,
UI 风格来源属于“要什么”的一部分,agent 实现前必须确认。

风格来源三选一:
1. 复用项目现有设计系统 / 相邻页面;
2. owner 给参考图、参考站、风格关键词;
3. agent 先给 2-3 个风格方向和取舍,等 owner 拍板。

不产出用户可见界面的任务不触发:
脚本、后端接口、数据清洗、配置、测试、重构,不问 UI 样式。

已有界面内的小修、小 bug、文案微调:
默认沿用现有样式,不单独问;只有无现有样式可沿用、或新增 / 大改视觉界面时才问。
```

## 6. 落点设计

### 6.1 `STANDARD.md`

最小改动:

- §1.2 “产品形态”下补一句:对新增 / 大改 UI,还要确认“UI 风格来源”。
- §1.3 “收口标准”从“验收 + 主流程 + 范围 + 形态”扩为“验收 + 主流程 + 范围 + 形态 + UI 风格来源(仅 UI 任务)”。
- §1 附“分流”保留现有低风险 carve-out,并加一句反向边界:无 UI 任务、已有界面小修不触发样式确认。

### 6.2 `master/base/AGENTS.md`

在 always-loaded 内核只加短句,不展开设计流程:

- 人机分工行在“产品形态”后加“新增 / 大改 UI 需确认风格来源”。
- 沟通分流行补“新增 / 大改 UI 且风格来源不明 -> 先确认;脚本 / 后端 / 既有样式小修 -> 不问样式”。

### 6.3 `skills/sop-audit/SKILL.md`

把它纳入沟通闭环 / 结构缺失检查,但不新增主线表:

- 若项目 `AGENTS.md` 只写“确认形态”,没有 UI 风格来源闸,且项目有前端 / App / 可视化界面,报 P3 `missing`。
- 若项目把脚本、后端、既有 UI 小修也强制样式确认,报 P2/P1 `over` 或 `nopushback`,按实际人手成本判。

### 6.4 `PLAYBOOK.md` 和 `experiments/`

新增一次实验记录,沉淀教训:

- 标题:有 UI 的任务,风格来源也是“要什么”;但样式确认必须窄触发。
- 证据:本次用户反馈 + 本 spec。
- 边界:只管新增 / 大改 UI,不管纯脚本和已有样式小修。

## 7. 运行示例

### 触发

用户说:“做一个后台页面,展示订单趋势。”

agent 应先问或给选项:

```text
这是新增可视化页面,实现前我需要确认 UI 风格来源:
1. 沿用项目现有后台样式;
2. 你给参考图 / 参考站 / 关键词;
3. 我给 2-3 个方向让你拍。
```

### 不触发

用户说:“写个脚本,把 CSV 转成 JSON。”

agent 不问样式,只确认输入、输出、异常处理和验收。

### 不触发

用户说:“把这个页面按钮文案从 A 改成 B。”

agent 默认沿用现有样式,不问 UI 风格。

### 触发

用户说:“重做首页,让它更高级。”

这是大改 UI 且风格模糊。agent 必须先确认风格来源,不能直接开改。

## 8. 验收标准

1. `STANDARD.md` 能搜到“UI 风格来源”或等义短语。
2. `master/base/AGENTS.md` 的 always-loaded 约束能让 agent 在新增 / 大改 UI 前确认风格来源。
3. `STANDARD.md` 和 `master/base/AGENTS.md` 都明确脚本 / 后端 / 数据处理 / 既有样式小修不触发样式确认。
4. `skills/sop-audit/SKILL.md` 能检查两类问题:该问没问;不该问却强制问。
5. 新增 `experiments/YYYY-MM-DD-NNN-ui-style-confirmation-gate.md`,并在 `PLAYBOOK.md` 只加入带实验编号的教训。
6. 本次改动净增行数保持克制;若超过约 25 行规则正文,需回炉合并到现有段落。

## 9. 反向验收

1. 不新增 `§1.11` 或新的大型章节。
2. 不新增 `ui_style[]` 参数表项;该配置可作为后续复发后的增强,本次先不做。
3. 不把 UI 风格确认写成所有前端任务必问。
4. 不把脚本 / CLI / 后端 / 数据任务拖进样式确认。
5. 不重抄外部设计 brief 模板。
6. 不改 `$superpowers:brainstorming` 插件缓存。

## 10. 风险与未验证

- 未在真实前端项目回灌验证;当前是本仓规则层设计。
- “新增 / 大改 UI”的识别依赖 agent 判断,需要在 `sop-audit` 中用示例辅助校准。
- 若项目本身已有强设计系统,未来可能需要 `ui_style[]` 或按端 UI house style;本次先不加,避免预建。
