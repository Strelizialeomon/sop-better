# Codex 三层引导协议设计

- **日期**:2026-07-05
- **状态**:已落地到 STANDARD / 母本 / sop-audit / exp-020
- **目标**:把 Codex 从“松散反馈 / 直接开工”改成“先带路、再动手”的协作方式,并写入 sop-better 的 SOP 层。

---

## 1. 问题

当前 Codex 在工作中容易出现两类体验问题:

1. **不带路**:只松散反馈一下,很少告诉用户下一步该怎么选。
2. **过早动手**:在目标、范围、验收、背景还没收口时,已经开始改代码或改文档。

这会让用户从“审稿人”退回“项目经理 + 需求补丁工”:用户既要补背景,又要追着纠偏。

---

## 2. 设计原则

采用“覆盖所有任务,但不阻塞所有任务”的原则。

- 所有回复都要帮助用户知道下一步。
- 只有目标 / 范围 / 验收缺口会影响实现、或动作不可轻易回滚 / 跨边界 / 高风险时,才必须等用户确认。
- 用户已明确要求、范围清楚、低风险的局部改动,允许直接做;动手前用一句话报告范围即可。
- 判断依据看 **Codex 下一步动作的后果**,不看用户有没有说“直接做”。

参考原则:

- [Microsoft HAX Guidelines](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/):AI 交互要帮助团队规划系统行为,暴露不确定性并支持用户控制。
- [Google People + AI Guidebook](https://pair.withgoogle.com/guidebook/):人机协作是双向反馈回路。
- [NN/g confirmation dialogs](https://www.nngroup.com/articles/confirmation-dialog/):确认适合防止重要错误,但不能滥用。
- [Apple HIG Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts):警告会打断用户,应留给重要问题或破坏性动作。

---

## 3. 三层协议

### 第 1 层:导航卡,不阻塞

适用:

- 解释概念
- 只读查询
- 看状态 / 看 diff
- 总结调研
- 给方案但不改文件

行为:

- Codex 可以直接完成只读动作。
- 有明显分叉时,回复最后给用户 2-3 个自然下一步。
- 简单事实 / 状态类回答只给 1 个推荐下一步;没有下一步时明确“到这里结束”。

格式:

```md
结论:
...

建议下一步:
...
```

### 第 2 层:确认卡,阻塞

适用:

- 下一步会改本地文件,且目标 / 范围 / 验收 / 背景仍有会影响实现的缺口
- 非简单改动,会跨模块 / 跨端 / 跨职责边界
- 改动不可轻易回滚,或失败成本明显高于普通局部补丁
- 新增 / 替换核心基建依赖、跨栈依赖、影响安全 / 成本 / 许可 / 部署的依赖、改核心配置 / 改 SOP 规则
- 用户要求“先讨论 / 不改文件”,但下一步可能进入实现

行为:

- Codex 不得直接动手。
- 必须先给三段式确认卡,等用户选择。
- 用户已明确要求、范围清楚、低风险的局部改动不进第 2 层阻塞;Codex 可直接做,但要先用一句话说明改动范围。

格式:

```md
我理解的目标:
...

缺口 / 风险:
...

下一步你选一个:
A. 按最小改动做
B. 先补方案 / spec
C. 先只检查不改
```

### 第 3 层:高危闸,强阻塞

适用:

- push / deploy
- 删除文件或数据
- git reset / rebase / force push
- 动生产环境
- 调用付费 API 或大批量任务
- 大范围重构

行为:

- Codex 必须明确动作、风险和影响范围。
- 等用户明确确认具体动作后才能执行。

格式:

```md
高风险动作:
...

风险:
...

请明确确认:
A. 执行
B. 先检查
C. 取消 / 改方案
```

## 4. SOP 落点

落三处规则文件,并补一条实验记录。不直接改外部 `$superpowers:brainstorming` 插件。

1. **`STANDARD.md`**
   - 把“三层引导协议”写成正式公约。
   - 说明它属于“说人话 + 主动建议 + 不假民主”的执行层。

2. **`master/base/AGENTS.md`**
   - 把协议放进生成项目的常驻指令。
   - 让每个项目打开 Codex 后立即生效。

3. **`skills/sop-audit/SKILL.md`**
   - 将“缺三层引导协议”列为沟通约束缺失。
   - audit 能提示老项目回灌。

4. **`experiments/2026-07-05-020-codex-guidance-protocol.md`**
   - 记录这次从用户真实痛点抽出的规则。
   - PLAYBOOK 只沉淀经 exp-020 背书的教训,不在 spec 阶段提前写结论。

不改 `$superpowers:brainstorming` 的原因:

- 它是外部插件缓存,升级可能覆盖。
- 它强制写 design doc 并进入 writing-plans,与 sop-better 的“跳 writing-plans,用验收 + review 补偿”规则冲突。
- 本问题是通用协作协议,不只属于 brainstorming skill。

---

## 5. 验收标准

- `STANDARD.md` 明确规定“三层引导协议”。
- `master/base/AGENTS.md` 生成物会要求 Codex:
  - 只读任务不阻塞,并给推荐下一步或明确结束。
  - 明确、低风险、局部的小改动不阻塞,但动手前简报范围。
  - 需求缺目标 / 范围 / 验收且下一步会实现时,先给确认卡。
  - 高危任务走高危闸。
- `skills/sop-audit/SKILL.md` 能检查项目是否缺这条协议。
- 新增 `experiments/2026-07-05-020-codex-guidance-protocol.md` 记录本次规则来源。
- 协议不要求所有动作都停下来确认,避免确认疲劳。
- 协议不靠判断用户措辞,只看动作后果。
- 不修改外部 `$superpowers:brainstorming` 插件缓存。

可检查场景:

1. 用户问“当前分支状态?” → Codex 可直接查,结尾给 1 个推荐下一步或说明已结束。
2. 用户说“把 README 里的错别字改掉”且范围清楚 → Codex 先一句话说明改动范围,然后可直接改。
3. 用户说“优化登录流程”但没说验收 / 范围 → Codex 必须给确认卡,不得改代码。
4. 用户说“推到远端 / 删除文件 / deploy” → Codex 必须给高危闸,等明确确认。

---

## 6. 边界

- 纯聊天 / 解释 / 只读查询不阻塞,但要给下一步。
- 用户明确要求“只讨论 / 不改文件”时,不得进入第 2 层执行。
- 用户明确要求 push / deploy 等高危动作时,仍按第 3 层执行;如果项目或全局规则已把该用户指令视为明确授权,可以执行,但必须先把风险说清。
- 如果协议使用后仍明显拖慢小任务,后续可继续收窄第 2 层;本轮先保留“明确低风险局部改动可直接做”的 carve-out。

---

## 7. 不做什么

- 不改外部插件缓存。
- 不恢复 writing-plans 流程。
- 不新增独立 skill。
- 不把所有只读问题都变成阻塞选择题。
