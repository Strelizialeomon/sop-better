# Codex 三层引导协议设计

- **日期**:2026-07-05
- **状态**:待用户审阅
- **目标**:把 Codex 从“松散反馈 / 直接开工”改成“先带路、再动手”的协作方式,并写入 sop-better 的 SOP 层。

---

## 1. 问题

当前 Codex 在工作中容易出现两类体验问题:

1. **不带路**:只松散反馈一下,很少告诉用户下一步该怎么选。
2. **过早动手**:在目标、范围、验收、背景还没收口时,已经开始改代码或改文档。

这会让用户从“审稿人”退回“项目经理 + 需求补丁工”:用户既要补背景,又要追着纠偏。

---

## 2. 设计原则

采用“覆盖所有任务,但不阻塞所有任务”的原则。

- 所有回复都要帮助用户知道下一步。
- 只有会产生本地副作用或高风险后果的动作才必须等用户确认。
- 判断依据看 **Codex 下一步动作的后果**,不看用户有没有说“直接做”。

参考原则:

- Microsoft HAX:AI 应暴露不确定性,支持用户纠正和控制。
- Google PAIR:人机协作需要持续反馈回路。
- NN/g confirmation dialogs:确认应保留给重要后果,滥用会制造确认疲劳。
- Apple HIG Alerts:警告会打断用户,应只用于重要问题或破坏性动作。

---

## 3. 三层协议

### 第 1 层:导航卡,不阻塞

适用:

- 解释概念
- 只读查询
- 看状态 / 看 diff
- 总结调研
- 给方案但不改文件

行为:

- Codex 可以直接完成只读动作。
- 回复最后必须给用户 2-3 个自然下一步。

格式:

```md
结论:
...

下一步你可以:
A. ...
B. ...
C. ...
```

### 第 2 层:确认卡,阻塞

适用:

- 改本地文件
- 改代码 / 改文档 / 改 SOP
- 生成新文件
- 安装依赖
- 改配置
- 需求缺目标 / 范围 / 验收 / 背景,但下一步会进入实现

行为:

- Codex 不得直接动手。
- 必须先给三段式确认卡,等用户选择。

格式:

```md
我理解的目标:
...

缺口 / 风险:
...

下一步你选一个:
A. 按最小改动做
B. 先补方案 / spec
C. 先只检查不改
```

### 第 3 层:高危闸,强阻塞

适用:

- push / deploy
- 删除文件或数据
- git reset / rebase / force push
- 动生产环境
- 调用付费 API 或大批量任务
- 大范围重构

行为:

- Codex 必须明确动作、风险和影响范围。
- 等用户明确确认具体动作后才能执行。

格式:

```md
高风险动作:
...

风险:
...

请明确确认:
A. 执行
B. 先检查
C. 取消 / 改方案
```

---

## 4. SOP 落点

落三处,不直接改外部 `$superpowers:brainstorming` 插件。

1. **`STANDARD.md`**
   - 把“三层引导协议”写成正式公约。
   - 说明它属于“说人话 + 主动建议 + 不假民主”的执行层。

2. **`master/base/AGENTS.md`**
   - 把协议放进生成项目的常驻指令。
   - 让每个项目打开 Codex 后立即生效。

3. **`skills/sop-audit/SKILL.md`**
   - 将“缺三层引导协议”列为沟通约束缺失。
   - audit 能提示老项目回灌。

不改 `$superpowers:brainstorming` 的原因:

- 它是外部插件缓存,升级可能覆盖。
- 它强制写 design doc 并进入 writing-plans,与 sop-better 的“跳 writing-plans,用验收 + review 补偿”规则冲突。
- 本问题是通用协作协议,不只属于 brainstorming skill。

---

## 5. 验收标准

- `STANDARD.md` 明确规定“三层引导协议”。
- `master/base/AGENTS.md` 生成物会要求 Codex:
  - 只读任务给导航卡。
  - 本地副作用任务先给确认卡。
  - 高危任务走高危闸。
- `skills/sop-audit/SKILL.md` 能检查项目是否缺这条协议。
- 协议不要求所有动作都停下来确认,避免确认疲劳。
- 协议不靠判断用户措辞,只看动作后果。
- 不修改外部 `$superpowers:brainstorming` 插件缓存。

---

## 6. 边界

- 纯聊天 / 解释 / 只读查询不阻塞,但要给下一步。
- 用户明确要求“只讨论 / 不改文件”时,不得进入第 2 层执行。
- 用户明确要求 push / deploy 等高危动作时,仍按第 3 层执行;如果项目或全局规则已把该用户指令视为明确授权,可以执行,但必须先把风险说清。
- 如果协议使用后明显拖慢小任务,后续可把第 2 层收窄为“非简单本地改动”,但本轮先按全覆盖上线。

---

## 7. 不做什么

- 不改外部插件缓存。
- 不恢复 writing-plans 流程。
- 不新增独立 skill。
- 不把所有只读问题都变成阻塞选择题。
