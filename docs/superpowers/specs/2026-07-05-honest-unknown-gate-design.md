# 诚实无知闸设计

- **日期**:2026-07-05
- **状态**:已按新眼睛意见补强,待 owner 复核后落地
- **目标**:把“知之为知之,不知为不知”落成 SOP 铁律:关键信息缺失时先查,查不到就明说,影响结果就打断确认,不替用户找补。

---

## 1. 问题

当前 SOP 已经有几条相邻规则:

- **反驳协议**:防止 agent 讨好用户、明知有问题却顺着说。
- **三层引导协议**:防止目标 / 范围 / 验收没收口就动手。
- **方案前调研包**:防止给方案前不查真实情况和主流做法。
- **缺上游交付物反弹不自补**:防止 agent 自己伪造需求 / 契约 / 验收。

这些规则方向都对,但缺一个更上位的总闸:当 agent 发现自己不知道、用户前提可能错、或任务缺关键信息时,必须先承认缺口并查证,不能用猜测把任务“顺”下去。

用户明确要求把传统中国智慧“知之为知之,不知为不知”应用到 SOP,并提出一组“八荣八耻”。这不是新增口号,而是要把“诚实无知”变成可检查的工作纪律。

---

## 2. 设计原则

### 2.1 不另造平行体系

本规则命名为 **诚实无知闸**。它是上位总闸,不是替代已有规则。

- 方案前需要建议时,继续走 **方案前调研包**。
- 本地动作会受缺口影响时,继续走 **三层引导确认卡**。
- 用户前提有错且有后果时,继续走 **反驳协议**。
- 缺的是上游角色该给的交付物时,继续走 **反弹不自补**。

诚实无知闸只补一刀:不知道就不能装知道,也不能替用户把错前提解释成“其实没问题”。

### 2.2 本地查询和互联网调研同等重要

本规则不能窄化成“只看本地代码”。用户特别强调此前已有分支专门处理互联网调研。现行脉络是:exp-016 把“实证 + 信源可信”放进 spec 新眼睛检查项,exp-021 把方案前查询沉淀成“方案前调研包”。

因此诚实无知闸要明确两条查询路径:

- **本地事实缺口**:先查代码、配置、日志、issue、PR、运行结果。
- **外部事实缺口**:涉及最新信息、第三方 API、平台规则、依赖版本、价格、安全、部署、合规、外部最佳实践时,先联网查可靠来源。

查不到、不能联网、没有权限、没时间实测时,必须标明“未联网 / 未实测 / 未查到 / 无权限”,再给保守建议。

### 2.3 打断任务是允许的

如果缺口会改变结果,agent 可以并且应该打断任务。

典型场景:

- 目标、范围、验收不清,继续做会做偏。
- 用户给的事实和代码 / 文档 / 公开资料不一致。
- 用户指定的 API / 平台规则 / 价格 / 版本可能已经变化。
- 用户把业务事实说得含糊,agent 继续推导会变成臆想业务。
- 任务依赖上游需求 doc / 契约 / 验收,但链接打不开或内容缺失。

打断不是甩锅。正确做法是先说清缺口、已经查了什么、还缺什么、为什么会影响结果,再请求确认或继续查证。

## 3. 八荣八耻

用户原始表达保留为记忆钩子:

> 以瞎猜盲动为耻,以认真查询为荣。  
> 以模糊执行为耻,以寻求确认为荣。  
> 以臆想业务为耻,以用户确认为荣。  
> 以重复创造为耻,以复用现有为荣。  
> 以跳过验证为耻,以主动测试为荣。  
> 以破坏架构为耻,以遵循规范为荣。  
> 以假装理解为耻,以诚实无知为荣。  
> 以盲目修改为耻,以谨慎思考为荣。

Agent-facing 的短版不写成纯口号,而写成执行规则:

> 关键信息缺失时,先查;查不到就说不知道;影响结果就打断确认。不得用猜测补业务事实、外部事实、验收标准或上游交付物。

八条不逐条新立规则,而是挂到现有闸上,防止重复造体系:

| 荣耻 | 已有规则 / 本次补强 | 触发条件 | 动作 |
|---|---|---|---|
| 瞎猜盲动 / 认真查询 | 本次诚实无知闸 + 方案前调研包 | 关键信息缺失、本地或外部事实不确定 | 先查本地凭据或联网查可靠来源;查不到就标未验 |
| 模糊执行 / 寻求确认 | 三层引导确认卡 | 目标 / 范围 / 验收 / 背景缺口会影响实现 | 先给确认卡,等 owner 选 |
| 臆想业务 / 用户确认 | 人机分工 + 反弹不自补 | 业务事实、产品形态、上游交付物缺失 | 标为业务前提,找 owner 或上游确认,不自己补 |
| 重复创造 / 复用现有 | 单一真相源 + 遵循既有模式 | 发现现有规范、模板、helper、文档可复用 | 优先引用 / 复用,新增前说明为什么现有不够 |
| 跳过验证 / 主动测试 | spec 可检验 + 任务收口卡 | 改文件、写文档、实现功能、排查问题 | 主动跑可用验证;不能跑就说明没跑和风险 |
| 破坏架构 / 遵循规范 | house_style + 架构边界 + 高风险闸 | 改跨模块 / 立栈 / 核心配置 / 架构边界 | 先对齐规范和现有结构;越界则确认 |
| 假装理解 / 诚实无知 | 本次诚实无知闸 | 不理解用户意图、事实、术语或约束 | 明说不确定,列缺口,先查或确认 |
| 盲目修改 / 谨慎思考 | 三层引导 + 局部补丁 carve-out | 下一步要改状态,且后果不清或不易回滚 | 低风险局部补丁可直接做;否则先说明风险并确认 |

实现时不需要把这张表全量塞进 always-loaded 长文。`STANDARD.md` 保留完整映射,`master/base/AGENTS.md` 放短版和关键执行句。

## 4. SOP 落点

### 4.1 `STANDARD.md`

在 `§1 公约` 的沟通约束区域新增 **诚实无知闸**。

建议内容:

- 关键信息缺失时,不得猜测推进。
- 本地事实先查本地真实凭据。
- 外部事实先联网查可靠来源。
- 无法查证时必须标未验。
- 用户前提可能错且有后果时,必须指出,不替用户找补。
- 缺口影响结果时,先确认再执行。
- 八荣八耻作为记忆钩子,执行以可检查规则为准。

同时在 `§5.3 沟通约束塌成口号` 中加入“诚实无知闸”,让 audit 能查。

### 4.2 `master/base/AGENTS.md`

在 `Agent 工作约束` 摘要中新增短条:

```md
- **诚实无知,不替人找补**:缺关键信息先查;本地事实查项目,外部事实联网查;查不到就说不知道;用户前提有误要指出;影响结果就打断确认。不得用猜测补业务事实、外部事实、验收标准或上游交付物。
```

在 `沟通约束` 中新增 “诚实无知闸”小节,放在“方案前调研包”附近。

小节应包含:

- 不知道就说不知道。
- 本地事实 / 外部事实分别怎么查。
- 查不到怎么标未验。
- 用户说错时怎么指出。
- 何时允许打断。
- 八荣八耻短版。

### 4.3 `skills/sop-audit/SKILL.md`

把 severity 映射中的 `P2 沟通约束塌成口号 / 过度阻塞` 扩展为:

```md
反驳 / 说人话 / 三层引导 / 方案前调研包 / 诚实无知闸 / 任务收口卡
```

Audit 应能识别:

- 只写“不要瞎猜 / 要认真 / 不懂就问”,但没有触发条件和动作。
- 没要求外部事实联网查,导致 agent 只靠训练记忆或本地猜。
- 没要求标明未联网 / 未实测 / 未查到 / 无权限。
- 没要求用户前提有误时指出,导致 agent 替用户找补。

Audit 也要保留反向边界:

- 低风险局部补丁不强制联网。
- 纯解释、稳定常识、无真实环境可摸的小事不强制调研包。
- 不能把所有问题都变成阻塞确认。

## 5. 行为示例

### 5.1 本地事实缺口

用户说“把登录逻辑改一下”,但没说验收。

正确行为:

- 先查现有登录流程和相关 issue。
- 如果验收仍不清,给确认卡。
- 不直接猜“应该是改按钮文案”。

### 5.2 外部事实缺口

用户说“用某平台接口做支付,应该支持 X 参数”。

正确行为:

- 先联网查官方文档 / changelog / SDK 源码或 release note。
- 若发现 X 参数已废弃或只在新版本支持,直接指出。
- 不说“可以的”来顺用户。

### 5.3 业务事实缺口

用户说“客户肯定都是企业用户”,但项目文档没有这个假设。

正确行为:

- 标出这是业务前提,需要用户确认或凭据支持。
- 可以给影响分析,但不把它写成已确认事实。

### 5.4 上游交付物缺失

issue 指向需求 doc,但远端打不开。

正确行为:

- 反弹上游,标 `待澄清`。
- 手上其它不被卡的工作继续。
- 不自己补一份“看起来合理”的需求文档。

## 6. 验收标准

用 `rg` 可快速检查,不能只查“诚实无知闸”这个词:

- `STANDARD.md` 出现 `诚实无知闸`。
- `STANDARD.md` 同时覆盖本地事实查询和外部事实联网查询,例如能命中:
  - `本地事实.*代码|配置|日志|issue|PR|运行结果`
  - `外部事实.*联网.*可靠来源`
  - `未联网|未实测|未查到|无权限`
- `master/base/AGENTS.md` 出现 `诚实无知,不替人找补`。
- `master/base/AGENTS.md` 不只保留八荣八耻短版,还要有执行句:缺关键信息先查、查不到说不知道、影响结果打断确认。
- `skills/sop-audit/SKILL.md` 将 `诚实无知闸` 纳入沟通约束审计。
- `skills/sop-audit/SKILL.md` 能查正反两面:
  - 正向:本地事实 / 外部事实 / 标未验 / 用户前提有误要指出。
  - 反向:低风险局部补丁不强制联网;不能把所有问题都变成阻塞确认。
- 新增实验记录 `experiments/2026-07-05-024-honest-unknown-gate.md`。
- `PLAYBOOK.md` 新增条目必须引用 exp-024。

场景验收:

1. “帮我选一个依赖” -> 触发方案前调研包,需要主流做法 + 信源凭据。
2. “这个 API 应该支持吧” -> 涉及外部事实,先联网查。
3. “改 README 错别字” -> 不触发联网调研,直接局部补丁。
4. “按这个业务假设做”但无凭据 -> 标业务前提,需要确认。
5. “issue 里的 doc 链接打不开” -> 反弹不自补。

## 7. 边界

- 不新增独立 skill。
- 不修改外部 `superpowers` 插件缓存。
- 不重复创造一套“联网调研协议”;联网调研继续落在现有“方案前调研包”里。
- 不把所有小事都变成阻塞确认。
- 不要求每次都写长报告;简单任务只要标清查证与未验。
- 用户明确说“不要联网 / 只按当前上下文”时,可以照做,但必须标明结论未联网验证。
