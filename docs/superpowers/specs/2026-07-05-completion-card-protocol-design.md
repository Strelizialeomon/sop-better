# 任务收口卡协议设计

- **日期**:2026-07-05
- **状态**:已落地到 STANDARD / 母本 / sop-audit / exp-022。
- **目标**:让 agent 做完一件事后,主动帮 owner 判断“现在到哪了、验没验、还差什么、下一步怎么选”,而不是只松散地说“完成了”。

---

## 1. 问题

当前 SOP 已经有“三层引导协议”和“方案前调研包”:

- 开工前能判断什么时候直接做、什么时候先确认。
- 给方案前能要求先调研、列主流做法、给建议。

但收尾还有缺口:任务做完后,agent 往往只汇报改了什么,没有稳定地帮 owner 收口。

具体表现:

- 不主动判断这件事是完成、基本完成、卡住,还是等 owner 决策。
- 没把验证结果和未验证部分摆清楚。
- 很少给 owner 一个推荐下一步。
- 有分叉时不给快捷选项,owner 还要自己追问“那我现在该干嘛”。

用户真正想要的是:agent 像靠谱协作者一样,多引导决策、多自检、多想方案;每次工作结束都能帮 owner 快速判断是否该收尾、继续、审查、推送或换方案。

---

## 2. 外部依据

调研结论支持把“完成定义 + 验证 + 下一步”写进 agent 常驻指令,但要按任务大小压缩,避免把小事做重。

- [OpenAI Codex best practices](https://developers.openai.com/codex/learn/best-practices):建议把“什么算完成、怎么验证工作”写进 `AGENTS.md`,并让 Codex 创建/运行测试、确认结果、review diff。
- [OpenAI AGENTS.md 文档](https://developers.openai.com/codex/guides/agents-md):Codex 会按全局和项目级 `AGENTS.md` 加载工作约定;项目规则适合承载这种可重复协作协议。
- [Scrum Guide Definition of Done](https://scrumguides.org/scrum-guide.html):Definition of Done 是对完成状态的正式描述,让所有人共享“什么叫做完”。
- [GitHub status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/about-status-checks):状态检查让提交是否满足条件变成可见状态;这说明“完成”不能只靠口头判断,要展示检查结果。
- [OpenAI Codex subagents](https://developers.openai.com/codex/subagents):子代理适合显式要求的多点 review;但会消耗更多 token,不应把每次小收口都强制升级成子代理。

结论:规则应叫“任务收口卡协议”。它不是新的重流程,而是把每次结束时本来就该说清的状态、验证、风险和下一步固定下来。

---

## 3. 协议

默认采用 **强引导 A**:每件事结束都要有收口动作。

但输出按任务大小自动压缩:

1. **小事一句话收口**
   - 适用:纯解释、只读查询、改错别字、无后续分叉的小状态回答。
   - 格式:`已完成/已解释;建议下一步是按推荐方案继续。` 或 `到这里结束,暂无下一步。`

2. **普通任务给收口卡**
   - 适用:改文件、写文档、调研、设计、排查问题、提交前后、review 后处理。
   - 必含五件事:
     - 当前状态:完成 / 基本完成 / 卡住 / 等你决策。
     - 验证结果:跑了什么检查;没跑什么也明说。
     - 风险遗留:还有什么没验、没做、可能错。
     - 推荐下一步:必须给 1 个明确建议。
     - 快捷选项:只有真有分叉时给 2-3 个选项,并标推荐。

3. **高风险 / 多分叉任务给决策收口卡**
   - 适用:push、deploy、合 PR、关闭 issue、删除、生产环境、付费 API、大范围重构、SOP 核心规则调整。
   - 行为:收口卡后必须给 owner 2-3 个可选动作,并推荐一个;高危动作仍受既有高危闸限制,不得把“推荐下一步”当成授权。

模板:

```md
状态:
完成 / 基本完成 / 卡住 / 等你决策

验证:
已跑检查项;未跑检查项

风险 / 未做:
未验证风险或遗留事项

建议下一步:
一个明确推荐动作

你可以选:
A. 推荐动作（推荐）
B. 备选动作
C. 暂停或改方案
```

---

## 4. 与现有协议的关系

任务收口卡不替代现有规则,而是补上“结束时”的闸。

- **三层引导协议**:管开工前和下一步动作是否要确认。
- **方案前调研包**:管给方案前是否先查真实情况。
- **任务收口卡**:管做完后是否帮 owner 判断状态、验证和下一步。
- **新眼睛 review**:仍是重要 spec / 代码完成后的独立安全网;收口卡要报告 review 是否已做,但不把每件小事都升级成子代理 review。
- **高危闸**:仍然最高优先级;收口卡可以推荐 push / deploy,但必须等 owner 明确确认具体动作。

一句话:开头用三层引导,中间用调研包和自检,结尾用收口卡。

## 6. 验收标准

- `STANDARD.md` 出现“任务收口卡协议”或等价规则。
- `master/base/AGENTS.md` 明确:
  - 小事一句话收口。
  - 普通任务默认五件套。
  - 有真实分叉时给 2-3 个快捷选项并标推荐。
  - 高危动作仍要 owner 明确确认。
- `$sop-audit` 把“缺收口卡 / 完成后无验证和下一步”列入沟通约束缺失。
- `experiments/2026-07-05-022-completion-card-protocol.md` 记录本次实验。
- `PLAYBOOK.md` 有 exp-022 背书条目。
- 反向边界保留:纯解释 / 小事不强制输出长卡片;没有下一步时可以明确“到这里结束”。

可检查场景:

1. 用户问“现在分支状态?” → agent 查完后一句话给状态 + 推荐下一步。
2. 用户让改一处文案 → agent 改完后说明改了什么、是否验证、建议是否提交。
3. 用户让实现一个需求 → agent 完成后给状态、测试/检查结果、风险、推荐下一步,例如 review / commit / push / 等 owner 验收。
4. 用户让 push → agent 先说明当前状态和风险,等明确 push 指令后执行;执行后报告远端是否对齐。
5. 任务卡住 → agent 不假装完成,必须说卡在哪里、已验证什么、推荐 owner 选哪个解法。

---

## 7. 边界

- 不要求每次都写长报告;小事一句话就是合格收口。
- 不要求每次都给选择题;只有真有分叉才给,否则给 1 个推荐下一步。
- 不把“建议下一步”当授权;push / deploy / 删除 / 改 git 历史等仍按高危闸。
- 不用收口卡掩盖未验证事实;没跑测试、没联网、没看远端就直说。
- 不因为“要多自检”就每次都派子代理;重要 spec / 代码按既有新眼睛规则,小事本线程自检即可。
