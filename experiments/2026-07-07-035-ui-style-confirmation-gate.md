# exp-035 · UI 风格确认闸

- **日期**:2026-07-07
- **真实任务**:用户反馈 Codex 在需求讨论清楚后会直接开干 UI,没有再确认界面样式;同时要求纯脚本任务不要被拖进样式确认。
- **本次撒手档位**:L3(改 STANDARD / 母本 / audit 规则,影响后续项目生成与审计)

---

## 1. 选活 + 定档

这是一个真协作痛点,不是抽象偏好。问题会影响所有后续有 UI 的项目:功能可能对,但视觉气质、信息密度、参考样式由 agent 默认填空。

爆炸半径:规则写太轻,agent 继续跳过样式确认;规则写太重,脚本 / 后端 / 既有样式小修都会被拖成确认疲劳。

## 2. 便宜验证方案(动手前必须答)

> 我怎么在 5 分钟内、**不逐行读**,就看出 AI 做对没?

- 验证手段:`rg` 查 STANDARD / 母本 / sop-audit 是否有“UI 风格来源”;查脚本 / 后端 / 既有样式小修是否被明确豁免;查没有新增 `ui_style[]` / `§1.11` / 大型新章。
- 如果上面答不上来 → 先补的功课是:把触发和反向边界写进 spec,再让 owner 确认。

## 3. 给 AI 的简报(只给目标+约束+验收,不给解法)

```
目标:
让 Codex 在新增 / 大改前端页面、App 页面、可视化界面前确认 UI 风格来源。

约束:
- 只管新增 / 大改 UI。
- 脚本、后端、数据处理、配置、测试、重构、既有样式小修不触发。
- 不新增 ui_style[] 参数。
- 不新开大章节,接到现有形态 / 收口 / 分流规则。
- 不改 $superpowers:brainstorming 插件缓存。

验收标准:
- STANDARD / master/base/AGENTS.md / sop-audit 都能搜到 UI 风格来源闸。
- 明确脚本 / 后端 / 数据处理 / 既有样式小修不为样式确认阻塞。
- PLAYBOOK 只加入带 exp-035 证据的教训。
```

## 4. AI 跑完,我来评

- **AI 做了哪些决策**(它替我想的部分):
  - 把“UI 风格来源”并进已有“产品形态 / 收口标准”,不另起新流程。
  - 把触发条件限定为新增 / 大改 UI,既有样式小修沿用现状。
  - 让 audit 同时查“该问没问”和“不该问却问”。
- **超出我预期 / 我自己想不到的地方**(← 爽感来源,最重要):
  - 用“风格来源”而不是“风格细节”收口,降低 owner 决策成本:可以复用现有设计、给参考,也可以让 agent 出 2-3 个方向。
- **翻车 / 我得纠偏的地方**:
  - `$superpowers:brainstorming` 默认要求进入 writing-plans,但本仓 STANDARD 明确跳过 writing-plans;本次由 owner 当场确认,按本仓流程直接实现。

### 评分(10 分制)

| 维度 | 分 | 备注 |
|---|---|---|
| 设计质量(它做得好不好) | 8/10 | 接在现有形态规则上,没有新建大流程 |
| 省力程度(比我自己干省了多少脑子) | 8/10 | 触发和豁免边界都写清 |
| **爽感**(有没有"卧槽这样也行") | 7/10 | “风格来源”比完整 UI brief 更轻 |
| 验证成本(检查它的结果累不累) | 8/10 | `rg` 正反向即可查大半 |
