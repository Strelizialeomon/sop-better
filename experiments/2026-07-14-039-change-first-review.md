# exp-039 · change-first 复审先看本轮变化,语义上下文按需展开

- **日期**:2026-07-14
- **问题**:代码只改了一小段后,每轮复审仍重新扫描完整任务甚至整个仓库,耗时过长。
- **目标**:比较“本轮 change + 相关语义上下文”和“完整任务 change”两种输入,确认前者是否在不漏已知缺陷的前提下降低耗时。
- **边界**:本实验只验证复审输入策略,不证明或要求任何客户端、任务控制器、守护进程或本地 agent 编排工具。

## 固定样本

- `baseline=db53a7a`
- `candidate=6384925d85034b29984e032f9f7bd5423da20cee`
- `defect=6b31592a380a36510da65dc65b107db9b03f18f3`
- Codex CLI 0.144.1 / high effort / read-only sandbox / Apple M5
- 交替运行 change-first 与完整任务复审,各 3 次。

固定三个跨边界缺陷:

1. 调用方把 merged commit 错当成已覆盖 HEAD。
2. change 基线错误退回 merge-base,导致覆盖区间不准确。
3. reset 后复用旧 finding ID,导致已关闭问题和新问题混淆。

这些缺陷都不是只看红绿两行就能判断;reviewer 必须顺着变化查看相关调用方、状态约束和测试。因此本实验中的 change-first 指“以 change 为入口,按需展开相关语义上下文”,不是把 reviewer 限制在 diff 行内。

## 结果

| 方式 | 3 次 wall time | 中位数 | 已知缺陷检出 |
|---|---|---:|---|
| change-first | `75.223 / 90.149 / 113.854s` | `90.149s` | 3 次均检出 T1 / T2 / T3 |
| 完整任务 change | `316.336 / 316.873 / 205.106s` | `316.336s` | 3 次均检出 T1 / T2 / T3 |

中位耗时比值为 `90.149 / 316.336 = 28.50%`,通过预设 `≤50%` 门槛;6 次都抓全固定缺陷。

## 结晶

- 首次复审覆盖“任务起点 → 当前 HEAD”的完整任务 change。
- 后续复审覆盖“上次已审 HEAD → 当前 HEAD”的全部新增 change。
- reviewer 可顺着 change 查看相关函数、接口、调用方、契约、测试和不变量,但不重新遍历无关仓库。
- 每轮记录已审 HEAD 与未关闭 findings;基线失效、历史不连续、任务范围不清或疑似漏改时,回退到完整任务 change。
- 回退范围默认是完整任务 change,不是整个仓库。
