# exp-005 · 给业务人员补"开工/收工"会话动作——但差点过度治理,被 owner 一句话拦下

- **日期**:2026-06-08
- **真实任务**:sop-better 自身改进——业务人员打开 Claude Code 后,补"开工(sync + 扫待我拍板的 issue)/ 收工(说收工 → 推收口 doc 远端)"两个动作 + 定"文档 main / 代码 PR"政策。
- **本次撒手档位**:设计阶段 owner 主导(brainstorming),实现 L2(我改 + 自验 + 新眼睛 review,owner 审 spec)。

---

## 1. 选活 + 定档

owner 提了三条业务侧前置/收尾动作。爆炸半径小(全是 markdown:STANDARD + templates + skills,可改可回滚)。但这活的真风险**不在代码、在 SOP 自身膨胀**——给一个"反过度治理"的工具加规则,最容易犯的就是它自己治的病。

## 2. 便宜验证方案

- **正向**:grep 确认 `待业务确认 / 收工 / 文档推 main` 落到该落的文件。
- **反向(关键)**:grep 确认**没**加不该加的(`§1.11`、新章节、新追加块、重抄的 sync/验链接正文)。
- **硬指标**:全部文件**净增行数 ≤ 25**,超了即"又膨胀",回炉。
- **新眼睛 review**:独立子代理三查(合规/bug/体量),要求先给最强反对。

## 3. 给 AI 的简报

```
目标:业务人员开工自动 sync + 扫待拍板 issue 一条条过;收工一句话把收口 doc 推远端。
约束:只在 C≥C1 生效;不新立概念;已有规则一律指针引用、绝不重抄(§1.6)。
验收:见 spec §5(正向 grep + 反向 grep + ≤25 行 + 新眼睛 review)。
```

## 4. AI 跑完,我来评

- **AI 替我想的**:把 owner 三条需求拆成"已有 vs 真缺"——发现 sync、验链接、doc 先推后开 issue、自检保真**早就存在**,真缺口只有两点(开工 surface 待拍板 issue + 文档 main 政策)。
- **⭐ 超出预期 / 最该记的**:**第一版我(agent)自己的提案是过度治理的**——立新 §1.11 公约 + "闭环"品牌 + 穿 7 文件各加一段 + 重抄 4 条已有规则。**是 owner 一句"这是否违反 better lighter 初衷"在写 spec 前就拦住了。** 我据此用 audit 的镜头审自己的草案,承认有罪,砍到 ~1/3(净增 6 行)。
- **翻车 / 纠偏**:新眼睛 review 又逮到一处真口子——always-loaded 的 `agent-constraints` 那行把"文档推 main"压成缩写、丢了"main 受保护则走 PR"护栏,下游 agent 可能硬推保护分支。补回。

## 5. 抽一条教训 → 回填 PLAYBOOK

**给一个反过度治理的工具加规则时,默认草案会犯它自己治的病(重抄已有 + 为小缺口立大概念)。** 改 SOP 前先用 audit 的镜头审自己的提案,且把"反向验收(grep 没加不该加的)+ 净增行数硬上限"写进 spec —— 否则"加功能"会悄悄变成"加仪式"。

另一条:**反驳闸是双向的**。owner 一句"是否违反初衷"在 spec 前就拦下了过度治理,比事后 audit 便宜得多。客观反驳不只是 agent 对 owner,owner 对 agent 的一句质疑同样是安全网。
