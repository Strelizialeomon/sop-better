## 1. 病灶:052 治了"审什么"的生成器,没治"审几轮"的循环

owner 症状与规则时间线对得上:exp-039(07-14 change-first)→ exp-049(07-23 步进表把复审钉进第 3 步)→ exp-052(07-28 ① 归零判据)。一个带 Issue 的需求 = spec 新眼睛 1 轮 + 代码首审 1 轮 + **每修一轮 findings 就再全权审一轮增量**,修 2 轮即 5 道审。

结构洞在 exp-052 自己的复审里就留了凭据(052 §4.1 ② 第 3 条,原文):"**STANDARD:47 写「① 天然收敛」,严格说只成立到'有上界'**(修一条 ① 的新代码可能违反另一条既存 doc → 下轮冒新 ①)"。即:052 把 reviewer 的**尺子**锁成有限集(只能引用已存在标准),但**每一轮的靶子**(新 diff)是新生成的——修复 diff 上可以合法冒出全新 ①,轮数没有不动点。owner 的 4-5 轮症状正是这条 ② 的实证。

## 2. 改法:A 修复核对制(主机制) + B 2 轮上限(兜底) + C 琐碎免核对(省确认轮)

### 2.1 与 exp-052 的张力,明着写

052 §2.1 刻意砍掉了"三轮上限 + 逐轮递减",理由"① 天然有上界——收敛是结构保证的,再加计数闸就是拿仪式补结构"。**本条部分恢复了轮数闸,不是打脸,是前提变了**:052 砍上限时以为收敛是结构保证的;052 自己的复审(② #3)+ owner 症状证明该前提只到"有上界"。本条先用 A 把收敛真正做成结构(第 2 轮起 reviewer 的授权从"全权新审"收窄为"核对修复",新问题除四类窄豁免外只能记 ②——生成器的输入被锁死,循环天然封顶);B 的 2 轮上限只兜"修不对反复核"这一种残余循环,是兜底闸、不是主机制。同轮顺手把 STANDARD:47 的"① 天然收敛"断言修正掉(052 ② #3 就此关闭)。

### 2.2 落定的规则

> 首轮全权 change-first 审;**第 2 轮起 reviewer 只核「上轮 ① 修没修对」**,不对修复 diff 全权新审——修复引入的新问题除四类窄豁免外一律记 ②。琐碎 ①(typo / 命名 / 一行修)修完自证、不占核对轮。**默认至多 2 轮**(首审 + 1 轮核对),核对后仍未闭的 ① 按 §1.9 escalate 上交 owner 拍板收口、不再自循环;owner 显式要求加轮不受此限。

预期轮数:spec 1 轮(琐碎免)+ 代码首审 1 轮 + 核对 0-1 轮 = **每需求 2-3 道审封顶**,对比现状 4-5+。

## 3. 调研依据(§1.4 信源分档 · 一手 / 二手分开)

**一手源**:

- **小意见不再来一轮**:Google eng-practices「LGTM With Comments」——reviewer 确信开发者会妥善处理、或建议是 minor(sort imports / typo 级)时,**批准同时留言、不等下一轮**;并明写个体响应速度比整轮流程更重要。已 WebFetch 核对原文。<https://google.github.io/eng-practices/review/reviewer/speed.html>(C 琐碎免核对的直接对应)
- **收口线是"更好"不是"完美"**:同站 standard.html"definitely improves the overall code health, even if not perfect",exp-052 §3 已核过,本条沿用。<https://google.github.io/eng-practices/review/reviewer/standard.html>

**二手源(只当线索,不为定义背书)**:

- agent 循环要三重停机(成功出口 + 迭代上限 + 预算上限),失败到限**转 escalation 而非再迭代**:verdent.ai 教程,SEO 内容,方向与 B 一致。<https://www.verdent.ai/guides/tutorial/build-coding-agent-loop>
- review 强度边际递减(>400 行 / >60 分钟检出率骤降;两名 reviewer 后收益递减):dev.to 综述引 SmartBear 研究,**未回 SmartBear 一手源核**。<https://dev.to/rahulxsingh/code-review-best-practices-the-complete-guide-for-engineering-teams-2026-52a4>
